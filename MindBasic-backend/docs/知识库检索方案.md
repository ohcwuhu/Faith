# 知识库检索方案（只用 DeepSeek）

> 2026-09-23。约束：账号里只有 DeepSeek 模型，没有 embedding 模型。
> 结论：**把检索从 Dify 搬到平台侧**，用 jieba + BM25 召回、DeepSeek 扩展与重排，
> 完全不依赖 embedding。

---

## 一、为什么 Dify 的检索用不了

| 路径 | 结果 |
| --- | --- |
| 语义检索 / 混合检索 | `Model provider langgenius/openai/openai quota exceeded`——默认 embedding 是 OpenAI，配额已超（DeepSeek 不提供 embedding） |
| 经济模式关键词检索 | 数据集「心理教练书籍」15 本、273 万字，索引状态全部 completed，但**连片段自己提取出的关键词都搜不到**：`教练` / `PCC` / `coaching` 全部 0 命中 |
| 速率 | 反复调用后报 `403 reached the knowledge base request rate limit of your subscription` |

也就是说，「普通心理教练」一直是在**没有资料**的情况下作答的。

## 二、方案

```
ASR 文本
   │
   ├─(并发) 多模态情感分析 ────────────────┐
   │                                       │
   └─ 知识检索（平台侧）                     │
        │  ① DeepSeek 查询扩展              │
        │     口语 → 检索关键词（含同义词）    │
        │  ② jieba + BM25 召回 top-12       │
        │  ③ DeepSeek 重排 → top-4          │
        ▼                                   ▼
   knowledge_context ──→ Dify 开始节点 ──→ 普通心理教练（提示词引用）
```

检索与多模态分析**并发执行**，所以 2~4 秒的检索耗时基本被隐藏，不拖慢回复。

用 DeepSeek 补的是 BM25 的两个短板：

- **查询扩展**：BM25 不认识「睡不着 ≈ 失眠」。实测把「一躺下就想工作的事，睡不着」
  扩成 `['失眠','入睡困难','工作压力','反刍思维','焦虑','睡前认知唤醒','放松训练','睡眠卫生']`；
- **重排**：BM25 只看词频，召回里混着噪声，交给 DeepSeek 按语义挑最相关的几条。

## 三、实测数据（15 本真实书籍）

| 指标 | 数值 |
| --- | --- |
| 切块 | 6,992 条（500 字 / 重叠 100 字） |
| 词条 | 51,969 个 |
| 构建耗时 | 8.5 s（一次性） |
| 索引文件 | 17.3 MB（`data/kb_index.pkl`） |
| 单轮检索耗时 | 查询扩展 0.5~2.1 s + 召回与重排 1.2~2.4 s |
| 运行成本 | 零 embedding 调用；每轮 2 次短 DeepSeek 调用 |

效果对比（「我总是拖延，明知道要做却不想动」）：

- 纯 BM25 top-1：一段关于"写作拖延"的 OCR 噪声片段；
- 加重排后 top-1：《教练心理学》中直接讨论拖延行为的段落。

## 四、已经落地的东西

| 文件 | 作用 |
| --- | --- |
| `app/services/ai_lab/kb_service.py` | 切块、jieba 分词、BM25 倒排索引、查询扩展、重排、`context_block_smart()` |
| `scripts/build_kb_index.py` | 构建索引（`--query` 可顺带验证检索） |
| `tests/test_kb_service.py` | 6 个单测，锁定切块 / 分词 / 检索 / 降级行为 |
| `socket_events.py` | ASR 后并发触发检索，结果作为 `knowledge_context` 传进 Dify |

构建命令：

```bash
cd MindBasic-backend
python scripts/build_kb_index.py --query "一躺下就想工作的事，睡不着"
```

书籍没变就只需构建一次；改过书目录后重新跑一次即可。

## 五、需要在 Dify 画布上做的（3 步）

### 1. 开始节点新增变量

节点「用户输入」→ 变量里加一个 **段落类型** 变量，名字必须是 `knowledge_context`
（与后端 `dify_inputs` 的键名一致）。

### 2. 「普通心理教练」提示词里引用它

建议追加这一段：

```
【参考资料】
以下是系统检索到的相关书籍片段，供你组织语言时参考：

{{knowledge_context}}

使用要求：
- 只在确实相关时参考，不要生硬照搬；
- 不要出现"资料1""检索结果""根据资料"这类字眼，像自己本来就懂一样自然表达；
- 资料与用户的实际情况冲突时，以用户说的为准；
- 资料为空或与本轮话题无关时，直接忽略，照常对话。
```

### 3. 把「知识检索」节点从主链路摘掉（建议）

它现在恒返回空，每轮白花 1~3 秒。改法：

```
条件分支 2 [false] → 知识检索 → 普通心理教练     （现状：检索是空的）
条件分支 2 [false] → 普通心理教练                （改后）
```

同时把「普通心理教练」的 **上下文** 开关关掉（它的输入 `知识检索.result` 已经没有意义）。
改动前请确认 `知识检索 → 普通心理教练` 与 `条件分支 2 [false] → 知识检索` 这两条线，
删掉后由 `条件分支 2 [false] → 普通心理教练` 接上。

改完导出 yml 覆盖仓库里的文件。

## 六、验证

```bash
cd MindBasic-backend
pytest tests/test_kb_service.py -q     # 检索逻辑
python scripts/check_dify.py           # Dify 链路（含知识检索命中数）
```

看两个点：

1. 后端日志里出现 `[1/5] 知识检索命中 N 字参考资料`；
2. 回复内容开始体现书籍里的说法（而不是泛泛而谈）——这是检索是否真正生效的**唯一判据**。

## 七、局限与后续可做

- **BM25 是词面匹配**：用户换了完全不同的说法时可能召回不到；靠查询扩展缓解，
  要彻底解决仍需 embedding（等账号有可用 embedding 模型后，可以把 `kb_service.search`
  换成向量检索，上层接口不用动）。
- **重排增加 2 次 DeepSeek 调用**：设 `KB_RERANK_ENABLED=false` 可退回纯 BM25，
  或调小 `KB_RECALL_CANDIDATES`（默认 12）降低成本。
- **切块还是通用策略**：正文里有 OCR 噪声和公式残渣，后续可以按章节标题做更细的切分，
  或对片段做一次清洗（去掉 `$...$`、页眉页脚杂讯）。
- **文本 AI 教练（非视频通话）还没接**：`ai_conversation_service.py` 走的是直连 DeepSeek，
  同样可以调 `kb_service.context_block_smart()` 把资料拼进提示词。
- **可调的参数**：`KB_CHUNK_SIZE` / `KB_CHUNK_OVERLAP` / `KB_RECALL_CANDIDATES` /
  `KB_RERANK_ENABLED` / `KB_LLM_TIMEOUT` / `KB_SOURCE_DIR` / `KB_INDEX_PATH`。
